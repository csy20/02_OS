# 02_OS security, bug, and stability audit

Audited revision: [afed18e1e03cdef2a1cf200d08000668072bc3d3](https://github.com/csy20/02_OS/commit/afed18e1e03cdef2a1cf200d08000668072bc3d3), the current master fetched on 2026-09-30. Prior issues 1–47 and their fixes were checked to avoid duplicate open reports. Findings are tied to this revision; later fixes can change the assessment.

## Assessment

**Alpha / experimental developer environment. Production readiness is not established.** The custom runtime has reproducible privacy-boundary problems and ordinary-development failures. The desktop overlay is missing dock resources, the documented manual image build ships obsolete runtime binaries, and the installer has no provisioning step for a persistent 02_OS target. These are material integration defects even though the existing Rust tests pass.

No numeric stability percentage is justified: there is no measured boot/hardware/install pass-rate or soak dataset in this audit. A passing code test suite is evidence about the tested code paths, not the complete OS.

## Scope and evidence

Reviewed production source and relevant tests across all nine Rust crates: core, Git, parser, index/storage/graph/GC, memory/pipeline/staleness, context, MCP, daemon, and CLI. Reviewed the first-party build/release and user/session scripts, boot manifests, package list, permissions, credentials, service enablement, desktop defaults, and extension integration. Generated icons were checked for XML validity. For the vendored GNOME extensions, import/resource integrity and helper integration were examined; this is not a line-by-line security certification of every upstream function.

Validation used temporary Git repositories and synthetic marker data. Actual API/CLI fixtures reproduced repository symlink reads/writes, content reverts, dataset graph contamination, scanner/GC/fingerprint defects, Unicode parser panic, context privacy/budget/evidence defects, daemon untracked-only updates, and CLI/security-report contracts. GJS loading reproduced missing dock dependencies; a mocked Docker build reproduced unsafe scratch-directory deletion. Packaged-versus-source executable comparison demonstrated stale-binary permissions and missing commands. Installer and launcher findings are source/dependency traced; a graphical or disk installation was not executed.

- Existing `cargo fmt --all -- --check`: passed.
- Strict `cargo clippy --offline --locked --workspace --all-targets -- -D warnings`: passed.
- Existing `cargo test --offline --locked --workspace`: all **38 tests passed** when run with temporary Unix-socket access. The initial sandbox run stopped at a denied socket bind; that was an environment restriction, not a code failure.
- New process/profile validation: all **13 tests passed**, including a real daemon socket and semantic graph-edge assertions.
- Strict GLib schema dry run and desktop entry validation: passed (one harmless category hint).
- GJS dock module loading: failed as reported in #67.
- Systemd parser: rejected the ProtectHome value as reported in #70. Target service startup was not measured.

**Not performed:** full ISO assembly, BIOS/UEFI boot, graphical acceptance, installation to disk, GPU/Wi-Fi/audio/suspend hardware matrix, long-duration soak, or complete dependency-advisory/supply-chain scanning. The audit therefore does not certify kernel, hardware, or installed-system reliability.

## Fix order

1. Close repository read/write boundaries and ensure privacy filtering applies to returned context (#49, #50, #56, #57); align packaged binaries with source (#69). These affect whether private developer data can be trusted to this runtime.
2. Restore ordinary indexing reliability: content revert and Unicode parsing (#51, #58), then daemon freshness, dataset isolation and GC (#52, #55, #63).
3. Complete and validate desktop/installation packaging (#67, #68, #70–#72). Build-scratch protection must precede any automated privileged build.
4. Correct memory/evidence selection and budget/CLI contracts (#59–#66), and scanner configuration (#53–#54).
5. Add each issue's failing regression before its fix, then make the repaired test mandatory. Establish image/boot/install acceptance before declaring a stable release.

## Pull request and release tests

The accompanying test proposal adds `os-profile` and `runtime-smoke` jobs on every PR and push to master, alongside the existing `check` job. It locks Cargo dependency resolution, gives workflows read-only repository permissions, and sets timeouts. Runtime fixtures isolate XDG state; profile tests never execute the installer or root customization.

The repository ruleset or branch protection must require **check**, **os-profile**, and **runtime-smoke** to block merging on failure. That repository setting was not changed as part of this audit. Existing defects remain filed issues; the test proposal does not claim to fix them or cover every negative case already.

See [testing.md](testing.md) for local commands, precise regression suggestions, and a staged plan for disposable ISO build, BIOS/UEFI boot, desktop/service/privacy checks, install/reboot, updates, and soak testing. Require the complete image/installation suite for release and for OS packaging changes once a dedicated disposable VM runner is available.
